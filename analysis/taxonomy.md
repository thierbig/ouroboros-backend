# Failure-Mode Taxonomy

Generated by the investigator from `analysis/dumps/` on 2026-04-13.

## Corpus size

The MongoDB corpus is small: **19 total sessions, 453 chunks**. All sessions
are recorded with `status="completed"` (the backend never writes `running`,
`error`, or `abandoned` end-states at session-level), and all chunks have
`status="ok"` with `error=null` (the chunk writer never records LLM-level
errors at chunk granularity either). The spec's four stuck-detection criteria
therefore catch only 1 session by themselves (the `error_message` case).

To produce a useful taxonomy, the investigator added a **fifth criterion** —
`last chunk has tool_calls` — which flags sessions whose recorded stream
ended before the agent emitted a terminal assistant-without-tool-calls
message. This catches 7 stuck sessions, and is the signature of: WS
disconnect mid-loop, the user closing the tab while the agent is still
calling tools, or an unhandled backend exception that stopped chunk writes
without updating session status.

| Metric | Value |
|---|---|
| Total sessions in Mongo | 19 |
| Stuck under spec's 4 criteria | 1 |
| Stuck under expanded criteria (`ended_mid_loop`) | 7 |
| Golden candidates (non-stuck) | 12 |

The small N means counts below are **indicative, not statistically
significant**. The dominant bucket (foundry-install-loop) is unambiguous —
it appears in 6 of 7 stuck sessions. The other buckets are single- or
double-example singletons.

## Bucket 1: `foundry-install-loop` (count: 6)

### Definition
The session ends mid-loop while the agent is still trying to install or invoke
Foundry (`forge`, `foundryup`). The transcript contains repeated cycles of:
- `forge init` → "command not found"
- `curl -L https://foundry.paradigm.xyz | bash`
- `foundryup`
- `source ~/.bashrc && foundryup`
- `export PATH="$HOME/.foundry/bin:$PATH" && forge ...`
- `PATH="$PATH:$HOME/.foundry/bin" forge install ...`

The final recorded chunk always has `tool_calls` pointing to a `terminal` call
that is another variation of the above.

### Count
**6** stuck sessions (86% of stuck set; 32% of all sessions).

### Example session IDs
- `69cafdd3c9ee05a19b45638a` — 13 chunks, $0.22, last 7 chunks are PATH loop
- `69cb280662972386aaf55ff4` — 17 chunks, $0.37, forge install pyth-crosschain looping
- `69cc0171365f162bc336119f` — 19 chunks, $0.52, forge + bun mix
- `69cc5c542447cfb1b234d419` — 7 chunks, $0.14 (E2E test artifact, short loop)
- `69cc5d252447cfb1b234d422` — 4 chunks, $0.08 (initial "Coin Flip" game)
- `69caf6db825fef911ec3ebd3` — 24 chunks, $0.50 (resume session, also foundry)

### Chunk excerpt (from `69cafdd3c9ee05a19b45638a`, chunks 7–13)
```
#7  terminal: forge init --force .
#8  terminal: curl -L https://foundry.paradigm.xyz | bash
#9  terminal: source ~/.bashrc && foundryup
#10 terminal: export PATH="$HOME/.foundry/bin:$PATH" && foundryup
#11 terminal: export PATH="$HOME/.foundry/bin:$PATH" && foundryup
#12 terminal: export PATH="$HOME/.foundry/bin:$PATH" && forge init --force .
#13 terminal: export PATH="$HOME/.foundry/bin:$PATH" && forge install pyth...
[session ends]
```

### One-line hypothesis
`curl | bash` only installs the `foundryup` bootstrapper; `foundryup` itself
downloads forge/anvil/cast and edits `.bashrc`, but either (a) the next
`wsl bash -i -c` invocation caches a stale PATH, or (b) the foundryup
binary-download step exceeds the terminal tool's 180s timeout and the agent
resumes before forge is actually on disk — then loops on `export PATH`
variants instead of pivoting to the already-provided `pyth_deploy` tool
(`core/registry.py`) which handles forge build+deploy internally.

## Bucket 2: `api-tool-result-mismatch` (count: 1)

### Definition
Session ends with `error_message` set to an Anthropic API 400: `tool_use ids
were found without tool_result blocks immediately after: toolu_...`. The
agent loop crashed in the middle of multi-tool-call message construction;
history persisted to Mongo has a `tool_use` assistant message that was never
paired with a `tool` response before the next LLM call.

### Count
**1** session (14% of stuck set).

### Example session IDs
- `69c5c96fd00e0eacbd9bc64f` — 41 chunks, $2.54 (highest-cost session in the
  corpus; error at chunk 17 per the error_message, but 41 chunks total means
  subsequent retries also logged)

### Chunk excerpt (error_message from session doc)
```
Error code: 400 - {'type': 'error', 'error': {'type': 'invalid_request_error',
'message': 'messages.32: `tool_use` ids were found without `tool_result`
blocks immediately after: toolu_01L7ExZhZQGj1NFN...
```

### One-line hypothesis
When an assistant message has N parallel `tool_call` entries and one of them
raises in `registry.dispatch` *between* `history.append(assistant_msg)` (at
`core/agent.py:121`) and the per-tool-call `history.append(tool_msg)` (at
`core/agent.py:157`), the remaining tool_call ids in that message are left
without tool_result siblings — the next Anthropic request then 400s.

## Bucket 3: `bun-vite-scaffold-fallback` (count: 2)

### Definition
`bun create vite .` fails — either because the working directory contains
dotfiles/CLAUDE.md that the scaffolder refuses to overwrite, or because the
agent ran `bun init` beforehand (which the system prompt at
`core/prompt.py:22` explicitly forbids). Agent tries `rm -rf *`, `bun init
-y`, `rm -rf * && bun create vite .` in some order, then falls back to
writing `package.json`, `vite.config.js`, `index.html`, `src/main.jsx`
manually.

### Count
**2** sessions (fallback path visible; agent did or did not recover).

### Example session IDs
- `69cc0171365f162bc336119f` — 19 chunks, stuck: tried `bun create vite`,
  `bun install`, `bun init -y`, `rm -rf * && bun create vite .`, then wrote
  package.json/vite.config.js/index.html by hand; ended on `bun run dev`
- `69c5c96fd00e0eacbd9bc64f` — 41 chunks, stuck (also bucket 2): mixed bun
  vite + foundry; wrote package.json/vite.config.js/main.jsx manually after
  scaffold failed

### Chunk excerpt (from `69cc0171365f`)
```
#6  terminal: bun create vite . --template react
#7  terminal: bun install
#8  terminal: bun init -y
#9  terminal: rm -rf * && bun create vite . --template react
#11 write_file: package.json
#12 write_file: vite.config.js
[manual scaffold continues]
```

### One-line hypothesis
The working directory is seeded by the backend with a `CLAUDE.md` (and
possibly other metadata files) before the agent starts, so `bun create vite
.` refuses — the `rm -rf *` recovery leaves dotfiles intact; the system
prompt's "use `rm -rf .[!.]* * 2>/dev/null`" rule is buried in a paragraph
and the agent consistently ignores the dotfile glob.

## Bucket 4: `empty-resume-context` (count: 1)

### Definition
The initial user message is a short control word ("resume") with an empty
`history=[]`. The agent has no prior state to continue from, so it
improvises — picks a default game type and starts scaffolding — and ends up
in one of the above buckets anyway.

### Count
**1** session.

### Example session IDs
- `69caf6db825fef911ec3ebd3` — 24 chunks, $0.50, initial message = "resume"

### Chunk excerpt (from `69caf6db825f`, chunk 1 response)
```
I need to understand what you'd like me to resume or work on. Could you tell
me:
[...]
```
(followed by the agent deciding on its own to build a coin-flip game and
entering foundry-install-loop by chunk 10)

### One-line hypothesis
The frontend (or the /api/agent websocket handler) emits "resume" without
re-hydrating the session's `messages` array, so `Agent.run(...)` is called
with `history=[]`; the agent's recovery heuristic is to start from scratch
with an arbitrary game, which wastes iteration budget.

## Bucket 5: `interpreter-drift-shell-mixing` (count: 3, cross-cutting)

### Definition
Within foundry-install-loop sessions, the agent cycles between Unix, cmd,
and PowerShell invocations: `ls -la` → `dir` → `cmd /c "bun install"` →
`powershell -c "Invoke-WebRequest..."`, even though the terminal tool
(`tools/terminal.py:11`) always runs commands inside WSL bash. This
multiplies retry count without ever resolving the underlying problem.

### Count
**3** sessions exhibit the pattern strongly; all within other buckets.

### Example session IDs
- `69c5c96fd00e0eacbd9bc64f` — uses `cmd /c`, `powershell -c`,
  `winget install`, `rmdir /s /q` alongside bash commands
- `69cb280662972386aaf55ff4` — uses `bash -c "..."`, `PATH="..." forge ...`,
  `export PATH=...` variations
- `69cafdd3c9ee05a19b45638a` — cycles `source ~/.bashrc`, `export PATH=`,
  positional `PATH=... forge ...`

### Chunk excerpt (from `69c5c96fd00e`, chunks 6–9)
```
#6  terminal: curl -L https://foundry.paradigm.xyz | bash
#7  terminal: powershell -c "iwr -useb https://raw.githubusercontent.com/..."
#8  terminal: winget install --id Foundry.Foundry
#9  terminal: mkdir foundry-temp
```

### One-line hypothesis
The system prompt says "Commands run in Linux (WSL)" but the agent,
encountering any terminal error, flails across shell paradigms instead of
trusting the documented environment — prompt guidance is not sticky enough
against tool_error feedback.

## Frontend/transport artifacts

None of the 7 stuck sessions show signs of frontend causing the stuck state.
All 7 have chunk streams ending on an `assistant` message containing
`tool_calls`, with the preceding chunks making coherent forward progress —
this is the signature of the backend agent loop *actually* being busy with
tools when the session ends, not a UI render bug. See
`analysis/frontend_followups.md` for detail (file not emitted: no cases).

## Notes not actioned

- `core/agent.py:22` defaults to `max_iterations=100`, but `README.md:40`
  claims the budget is 25. None of the 19 sessions hit either number (max
  observed: 60 chunks in `69cb2d478d2c`). The doc/code drift is real but
  **not causal** for any stuck session in this corpus. Flagged per the
  spec's risks-and-mitigations row about stale docs.
- `core/agent.py:63` (budget warning injection) fires at 70% and 90% of
  `max_iterations`. At a 100-iter budget, neither trigger is reached in any
  observed session. If the budget were lowered to 25, six of the recovered
  not-stuck sessions (≥25 chunks) would have been interrupted by the warning
  — something to hold in mind if a fixer proposes lowering the default.
